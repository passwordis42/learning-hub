# 部署前提

这里只说明同一套同源入口如果要放到一台服务器上，主机环境还缺什么。仓库里的远程模式已经有代码和测试，但没有部署，也没有当成生产环境验证。默认 `npm run serve` 仍然只监听 `127.0.0.1`。

最终使用方式是打开已经部署好的网页，在设置里保存供应商密钥，然后由这台同源服务器去调用模型。使用者不需要在自己的电脑上启动程序。供应商密钥以后由运营者安全地交给设置页，不写进仓库。没有密钥只是还不能做真实模型调用，不挡住这套入口本身。

远程模式不会从“用户以后会提供 API”推断出可以公开、匿名地代持密钥。不设置 `HUB_EXPOSURE=remote` 时，监听地址保持 `127.0.0.1`，即使进程里有 `HUB_BIND` 也不会改到其他地址。

## 必须由主机环境提供

- HTTPS。Node 进程不直接对外提供 TLS。前面要有反向代理，把 `X-Forwarded-Proto: https` 传给本机端口，并设置 `HUB_TRUST_PROXY=1`。没有这层 TLS，远程模式会拒绝助手接口。
- 公开源和主机名单：`HUB_PUBLIC_ORIGIN=https://你的域名`，`HUB_ALLOWED_HOSTS` 包含该主机。其他 Host、Origin 和跨站请求不能建立会话，也不能改配置或调用模型。
- 管理口令：`HUB_ADMIN_TOKEN`，至少 32 个字符，放在主机的密钥存储里，不写进仓库、镜像或页面源码。设置页把它叫管理口令，用来打开设置；它不是模型密钥，也不是新的用户账号。
- 密钥文件持久化：`server/secrets/assistant-config.json` 或 `ASSISTANT_CONFIG_PATH` 指向只属于该服务用户的磁盘，权限 `0600`。换机器或重建容器时要保留这个文件，否则已保存的供应商密钥会丢。不要把它放进镜像或对象存储的公开位置。
- 反向代理只把流量转到本机回环地址。不要把 Node 端口公开到网上。只有在明确知道代理拓扑时才设置 `HUB_BIND`；远程模式不设置它时仍绑定 `127.0.0.1`。
- 进程以专用系统用户运行。本机模式挡不住同一个系统用户读取会话文件；远程模式靠管理口令、HTTPS 和主机名单，不靠“谁都能访问 127.0.0.1”。

## 明确不做

- 不提供注册、登录账号或云同步。
- 不把助手接口做成不带管理会话的公开代理。匿名请求不能替换上游，也不能拿已经保存的供应商密钥向外呼叫。
- 不在页面、脚本或日志里回显模型密钥、管理口令或访问口令。
- 这次不申请域名、证书、主机，也不启动远程进程。

示例变量在 `deploy/remote.env.example`。把它复制到主机的密钥管理，不要提交填好的文件。
